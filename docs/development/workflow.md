# Development Workflow and Reminders

This document is the canonical location for project-wide development workflows,
build hygiene, generated-file handling, and recurring reminders. Put
module-specific behavior in the corresponding document under `docs/modules/`.

## SigmaStudio Changes

Treat the files generated by a SigmaStudio compile and export as one versioned
unit. A schematic change can relocate parameters even when the affected block
itself was not edited.

For example, inserting parameters before a switch can move its control address
from `0x2030` to `0x204C`. The application address, DSP program, and initial
parameter image must all come from the same SigmaStudio export.

After changing SigmaStudio blocks, connections, parameters, or generated files:

1. Compile the complete SigmaStudio design.
2. Export and replace the complete corresponding file set under
   `src/SigmaStudioFiles/`. Do not update only a parameter-address header.
3. Review the generated-file diff for unexpected omissions or partial exports.
4. Perform a pristine firmware build.
5. Flash and reset the target, then validate the actual audio behavior as well
   as the control logs.

Use the pristine option supported by the chosen build path:

- With `west build`, pass `--pristine`.
- With `tools/buildprog/buildprog.py`, pass `--pristine`.

### Why a Pristine Build Is Required

The firmware compiles generated parameter addresses into application objects
such as `audio_control.c`. It separately compiles the generated SigmaDSP program
and initial parameter data into `adau1787.c`.

An incomplete incremental rebuild can therefore produce a valid firmware image
with mismatched parts:

```text
Application control object: new parameter address
Embedded DSP program:       previous parameter layout
```

The I2C transaction may succeed in this condition while reading or writing a
different parameter—or a location unused by the running DSP program. A pristine
build ensures the application control code and embedded DSP images are rebuilt
together.

Changing a C macro's name or adding an alias does not alter its numeric value
after preprocessing. If such an edit appears to fix a parameter-address issue,
the source edit or accompanying pristine build likely forced a previously stale
object to rebuild.

### When an Incremental Build Is Appropriate

An incremental build is normally appropriate for C-only changes that do not
modify:

- The SigmaStudio schematic
- Files under `src/SigmaStudioFiles/`
- Devicetree or Kconfig inputs
- The board, build type, sysbuild domains, or build-directory configuration

Use a pristine build whenever there is doubt about whether generated inputs and
compiled objects describe the same configuration.

## Generated-File Reminders

- Do not assume a SigmaStudio parameter address is stable across schematic
  changes.
- Reference the symbol from the current generated parameter header instead of
  copying its numeric address into application code.
- Keep application-level aliases descriptive, but remember that they do not
  provide address stability.
- Avoid manual edits to generated files; they will be overwritten by the next
  export. Make persistent behavioral changes in SigmaStudio or in
  non-generated application code.
- Check that all expected generated program, parameter, register, and metadata
  files changed together. Investigate an unexpectedly small or partial export
  before building.
- A log showing alternating RAM readback values proves that a location is
  writable. It does not, by itself, prove that the running DSP program assigns
  that location to the intended block.
